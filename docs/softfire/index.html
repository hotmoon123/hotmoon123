"The plan before the pixels" is not a mood. It is six short documents, in this order, written in plain language and yours to keep whether or not you go ahead. Anybody can promise six. So here are all six, filled in for the one project SoftFire has actually shipped — BiteKasa, a live food business.

The requirements

BiteKasa · public website · version 1

Goal
Someone who has never heard of BiteKasa can see the three packs, the price, what is in each one, and reach a human on WhatsApp in one tap — without an account and without paying online.
Who uses it
Customers deciding whether to order. The owner, who answers the messages.
Features, and how you would know each one works
FeatureWho uses itDone when
Show the three packs Customer Silver, Golden and Premium each show a price, a piece count and any drink
Separate fried / unfried / frozen pages Customer Each state has its own page, its own title and its own description
Order on WhatsApp Customer The message is pre-written and opens in WhatsApp addressed to the shop
Call from the phone Customer Tapping the number dials it, no copy and paste

Not in this version

No cart, no online payment, no delivery tracking, no customer accounts, no stock system, no database. Every order is a conversation, on purpose: the business takes orders by message today and building checkout before there is anyone to run it would be a costume, not a shop.

Two measurements it must pass, every deploy

JavaScript must stay under 150 KiB compressed and CSS under 20 KiB. Both are enforced by a script that fails the build if either is exceeded, so "make it fast" is a test result rather than a promise. A second script checks that all five pages carry a unique title and description, a correct canonical address, and appear in the sitemap.

Decisions still needed

  • Whether the two advertised numbers are both WhatsApp-enabled.
  • Whether the Silver, Golden and Premium prices apply to fried, unfried or frozen.
  • Whether GA4 is wanted at all — until it is, nothing is measured.
03 The app flow BiteKasa · every page, every button, every dead end

03

The app flow

BiteKasa · every page, every button, every dead end

An app flow is only useful if you can walk it. So this one is drawn in the standard six-shape flowchart notation — oval for a start or end, rectangle for an action, diamond for a decision, parallelogram for input, small circle for a connector, arrow for direction. If you can read a flowchart, you can audit this build. If you cannot, the reading underneath says the same thing in words.

Read as words

Home → the three packs → is this the right pack? If no, back to the packs. If yes, choose fried, unfried or frozen → Order on WhatsApp → the message is pre-written → the owner replies → the order is confirmed. At every point on that line, calling the shop is one tap away.

From any page

  • Call — taps straight into the phone dialler.
  • Instagram — opens the shop's profile in a new tab.
  • Privacy — one page, plain language, linked in the footer.

When something goes wrong

No WhatsApp installed WhatsApp offers to open in a browser or the app store. The phone number is printed beside the button so the order can still be placed by calling.
Visitor declines analytics Nothing is recorded, the site works identically, and the banner does not return.
Analytics key not set The banner never appears at all. There is no half-configured state.
Images fail to load Each image has written alt text, so the page still explains what was there.
Pack is out of stock The site says to confirm availability before ordering, so the website never promises stock it cannot see.

Read it for dead ends. Every branch above ends somewhere a person can still finish what they came to do — order food.

04 The design brief BiteKasa · colours, type, and the rules that keep screen ten on-brand

04

The design brief

BiteKasa · colours, type, and the rules that keep screen ten on-brand

Colours

  • Royal Red#A71920 Actions, pack tags
  • Warm Cream#F7EEDB Page ground
  • Royal Gold#D5A12E Golden pack, highlights

Type and rules

Fonts The brand's own two faces. No third face is introduced for a new page.
Buttons Red fill, cream text, rounded corners. One filled button per screen: Order on WhatsApp. Call is the quiet second.
Images Fixed ratios so the three pack photos line up. Any image that is not a real photograph is labelled illustrative, on the image.
Tone Warm and plain. "Ask about fried, unfried and frozen options", not "Explore our product range".
Honesty rule No invented shelf life, no ingredient or allergen claims, no delivery promise until delivery is real. Where the flyer is ambiguous, the site says "confirm".
Phone first Most customers arrive from Instagram on a phone. Designed at 390px and checked at 320 and 430 before desktop.

Read it for your real colour codes, not ones that look close. If a brief could describe any company's site, it is not specific enough.

05 The data sheet Two systems SoftFire built · what each one stores, and who can see it

05

The data sheet

Two systems SoftFire built · what each one stores, and who can see it

Two different answers, because the builds are different

BiteKasa stores nothing about a customer — no database, no login, no order record. An order exists only in the customer's WhatsApp thread and the owner's phone. That is not a missing feature; it is the smallest possible amount of personal data, which is the safest amount to hold. The Rent & Lease system is the opposite case — it holds real financial and personal records, so its data sheet is the one that actually matters. Both are below, with the source file for every claim.

A · BiteKasa website — nothing stored

Everything that could hold data, and what is actually in it
RecordWhat is storedWho can see it
CustomerNothing. No name, email or account is collected by the site.Nobody
OrderNothing in the site. The message exists only in WhatsApp.Customer and owner
PaymentNothing. No card is ever collected here.Nobody
AnalyticsPage views only, and only after the visitor accepts.The owner, in aggregate
Hosting logsGitHub Pages records standard web requests.GitHub

B · Rent & Lease system — records that matter

Ten record types, taken from the models in apps/*/models.py. The point of this table is the last column: for every record, exactly who may see it.

What each record holds, and who is entitled to see it
RecordWhat is storedWho can see it
Landlord · Tenant Email, name, phone. A landlord also has company name, business registration number and tax ID. That person, and the landlord they rent from
Building · Property Name, address, unit number, property type. The owning landlord; the tenant for their own unit only
Lease Dates, rent, deposit, status, the signed contract PDF. That landlord and that tenant
Invoice Amount, amount paid, due date, status, type. The landlord who issued it and the tenant it is for
Transaction Amount, provider, mobile-money number, gateway reference, idempotency key. The paying tenant and the receiving landlord
Payment method Provider, last four digits, expiry month and year. Never a full card number, never a CVV. Only the tenant who saved it
Maintenance ticket Title, description, priority, status, a photo, estimated cost. The tenant who raised it and the landlord of that property
Password reset token A single-use token tied to one account. Nobody — the system only

How a payment moves, and where the card stops

This is the part of a data sheet most people skip, and it is the part that matters. A sequence diagram answers one question: which system ever sees the card. Here the answer is visible in step 2 and step 4.

Rules that apply to both builds

  • No analytics script is injected until a visitor accepts. Declining is a real decline, not a delay.
  • The full card number is never stored. Only the provider, the last four digits and an expiry date. Card data belongs to the gateway.
  • Every transaction carries an idempotency key. A retried payment cannot be charged twice.
  • Leases soft-delete. deleted_at is set instead of the row being destroyed, so a disputed tenancy still has a history.
  • No card data is ever collected, so none can be leaked.
  • Product photographs of real customers are never published without permission.
  • If ordering is ever taken into the site, this document is rewritten before the first record is created, not after.

This is the one to never skip. A page that looks wrong can be fixed in an afternoon. A customer's data visible to the wrong people is a conversation you have with them.

The build order

BiteKasa · five stages, each ending in something you can check alone

What you get, and how you sign it off
StageWhat you getYou sign off when
1 · One page Hero, the three packs, one WhatsApp button You open it on your own phone and the prices are right
2 · The three states Separate fried, unfried and frozen pages Each page names its state and does not imply the others

5 · Launch Live address, QR artwork, daily uptime check A physical QR scan on a printed flyer opens the live site

Riskiest part first

Stage 1 put the prices and the WhatsApp handoff in front of the owner before any decoration existed, because a wrong price or a dead link is the only failure that actually costs a sale. Everything after stage 1 is additive and can be removed without breaking ordering.

Read it for a sign-off you can do yourself at every stage. If you cannot test it, you will only find out at the end.

The check before building starts

From the guide, unchanged. Ask any builder for each one. Tick it only if you have seen it and read it.

  • A design brief with our real colours and fonts
  • A plan for where client data lives and who sees it
