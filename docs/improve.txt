Shape Morph Ring Animation 

Using /hyperframes, create a 5-second seamless looping video (1080x1920, 30fps) of a shape-morphing ring animation centered on screen. Background is a soft mint green (#B8E6C8). The shapes are a deep forest green (#1B4332).
Setup: 8 identical shapes are arranged in a circle around the center point, evenly spaced at 45° intervals. Each shape is positioned on the ring at a consistent radius from center. The entire ring rotates slowly and continuously clockwise (one full rotation takes ~10 seconds, so across the 5-second loop it completes a half turn). Each individual shape also rotates on its own axis, always facing tangentially along the ring.
The morph sequence plays continuously across the 5 seconds. The shapes transition smoothly through these geometric forms in order, blending fluidly between each:
Phase 1 (0s–0.6s) — Diamonds/Rosette: 8 shapes start as a mix of squares and 45°-rotated diamonds arranged tightly, edges nearly touching, forming an 8-pointed star cutout in the negative space at center. Alternating shapes are rotated 45° relative to their neighbors.
Phase 2 (0.6s–1.2s) — Organic Blobs: Corners round dramatically. Shapes become soft organic blobs with high border-radius. They overlap slightly, creating a scalloped flower ring.
Phase 3 (1.2s–1.8s) — Teardrops/Petals: Shapes elongate into teardrop forms, pointed end facing center, round end facing outward. Arranged in a pinwheel — each petal tilted slightly clockwise, creating a spinning flower/windmill pattern.
Phase 4 (1.8s–2.5s) — Leaves: Shapes shrink slightly and morph into leaf/marquise shapes (pointed at both ends). The ring radius expands so there are visible gaps between each leaf. Individual rotation continues.
Phase 5 (2.5s–3.2s) — Semicircles: Shapes morph into half-circles, flat edge facing inward, round edge facing outward. Arranged in a gear-like ring pattern. Ring radius contracts slightly.
Phase 6 (3.2s–3.8s) — Rounded Triangles: Shapes become guitar-pick / rounded-triangle forms, still rotating individually, creating a turbine-like pattern.
Phase 7 (3.8s–4.3s) — Squares: Shapes grow into larger rounded squares, spread out on a wider ring radius. Each square is slightly rotated on its own axis, creating a loose octagonal arrangement. A faint thin circular guide line may be visible behind the shapes.
Phase 8 (4.3s–5.0s) — Arrows: Shapes morph into arrow/chevron shapes pointing inward toward center, tightly packed, forming a starburst/snowflake pattern with a star-shaped cutout in the negative space. This transitions seamlessly back to Phase 1 for the loop.
Key motion principles:

All shape morphs use smooth easing (power2.inOut) — no hard cuts between forms
The ring rotation is constant and linear (no easing) for a hypnotic feel
Individual shape rotation is slightly faster than ring rotation
The ring radius subtly breathes — expanding during looser arrangements (leaves, squares) and contracting during tighter ones (rosette, arrows)
The morph between shapes should animate border-radius, scale, aspect ratio, and rotation simultaneously

Implementation note: Each of the 8 shapes can be a single div with CSS transforms (translate for ring position, rotate for individual angle) and animated border-radius / width / height / clip-path for the shape morphing. Use GSAP timeline with morphSVG or clip-path interpolation for the shape transitions. Export as MP4 for Instagram Reel.

## SCOPE OF KNOWLEDGE — THE 5 LAYERS

### LAYER 1 — FRONTEND SECURITY

**The What:**
Define every frontend attack surface — XSS (Stored, Reflected, DOM-based), CSRF, Clickjacking, UI Redressing, Content Injection, Prototype Pollution, Subresource Integrity (SRI) failures, insecure client-side storage (localStorage, sessionStorage, IndexedDB, cookies), insecure deserialization in the browser, and supply chain attacks via npm/CDN.

**The Why:**
Explain why the browser is a hostile environment. Why the Same-Origin Policy exists, why it is insufficient alone, and why Content Security Policy (CSP) is the second line of defense.

**The How:**
- Implement CSP headers (strict, nonce-based, hash-based)
- HTTPOnly, Secure, SameSite cookie flags
- SRI for all third-party scripts
- Input sanitization vs. output encoding (DOMPurify, OWASP Java Encoder)
- Frame-busting and X-Frame-Options / frame-ancestors CSP directive
- Trusted Types API
- HTTPS everywhere — HSTS preloading
- Dependency auditing (npm audit, Snyk, Socket.dev)

**The Which/When/Who:**
- Which frameworks have secure defaults? (React auto-escapes JSX, Angular has DomSanitizer)
- When does CSP break third-party integrations?
- Who owns frontend security? (Security engineer + frontend engineer jointly)

**Architecture Consideration:**
Design a Frontend Security Architecture using: CDN with WAF (Cloudflare/Akamai), CSP policy management, SAST scanning in CI/CD (Semgrep, ESLint security plugin), and browser security headers as code (Helmet.js, security.txt).

### LAYER 2 — API SECURITY (REST / GraphQL / gRPC / WebSocket)

**The What:**
Define the API attack surface — Broken Object Level Authorization (BOLA/IDOR), Broken Authentication, Excessive Data Exposure, Rate Limit Abuse, Mass Assignment, Security Misconfiguration, Injection (SQLi, NoSQLi, Command Injection via API parameters), API versioning exposure, and GraphQL-specific attacks (introspection abuse, query depth attacks, batch attacks, field suggestions).

**The Why:**
APIs are the nervous system of modern software. They expose business logic directly. REST is stateless; that statelessness is a double-edged sword — no server-side session means JWTs must be hardened. GraphQL's flexibility becomes an attack surface without depth limiting and query cost analysis.

**The How:**
- OAuth 2.0 + OpenID Connect — authorization code flow with PKCE (not implicit flow)
- JWT best practices: RS256 over HS256, short expiry, token rotation, refresh token rotation, blacklisting on logout
- API Gateway pattern — rate limiting, throttling, IP allowlisting, authentication offloading (Kong, AWS API Gateway, Apigee)
- RBAC (Role-Based Access Control) and ABAC (Attribute-Based Access Control) — enforce at the service layer, not just the API layer
- Input validation and schema enforcement (OpenAPI/Swagger contract validation, Zod, Joi, Pydantic)
- GraphQL security: disable introspection in production, implement query depth limits, persisted queries, query cost analysis (graphql-depth-limit, graphql-query-complexity)
- gRPC security: mutual TLS (mTLS), protobuf validation, service mesh (Istio/Envoy)
- CORS policy hardening — no wildcard origins in production

**Architecture Consideration:**
Design an API Security Architecture using: API Gateway → Authentication Service (OAuth2/OIDC) → Rate Limiter → WAF → Load Balancer → Microservices. Include API versioning strategy, deprecation policy, and API contract testing (Pact).

---

### LAYER 3 — BACKEND / APPLICATION SERVER SECURITY

**The What:**
Define backend threats — Injection (SQL, NoSQL, OS Command, LDAP, XML/XPath), Insecure Direct Object Reference (IDOR), Business Logic Flaws, Server-Side Request Forgery (SSRF), Server-Side Template Injection (SSTI), Deserialization attacks (Java, Python Pickle, PHP Object Injection), Path Traversal, Race Conditions, XML External Entity (XXE) attacks, and Denial of Service at the application layer.

**The Why:**
The backend holds the business logic, the sensitive data, and the trust. It's the decision-making layer. A flaw here invalidates every frontend and API security control.

**The How:**
- Parameterized queries / Prepared Statements — always. ORM security (Hibernate, SQLAlchemy — avoid raw query interpolation)
- Principle of Least Privilege for every service account, DB connection, and internal API call
- Secrets management — HashiCorp Vault, AWS Secrets Manager, Azure Key Vault. Never in .env committed to version control
- Dependency management — OWASP Dependency-Check, Renovate, Dependabot, Software Bill of Materials (SBOM — CycloneDX, SPDX)
- SAST in CI/CD — Semgrep, SonarQube, Checkmarx, Veracode
- DAST — OWASP ZAP, Burp Suite Pro in automated CI pipeline
- Code reviews with security checklist — OWASP Code Review Guide
- Secure error handling — no stack traces to clients, structured logging with correlation IDs
- SSRF mitigations — block internal IP ranges (RFC 1918), use allowlists for outbound HTTP calls
- Deserialization — never deserialize untrusted data; use JSON over binary formats; validate schema before deserializing
- Thread safety, mutex/semaphore use for race condition prevention

**Architecture Consideration:**
Design a Secure Backend Architecture using: Hexagonal Architecture (Ports & Adapters) for security boundary clarity, Domain-Driven Design bounded contexts for access control separation, immutable infrastructure (containerized with Dockerfile hardening — non-root user, read-only filesystem, no privileged containers).

### LAYER 4 — MIDDLEWARE SECURITY

**The What:**
Define middleware — message brokers (Kafka, RabbitMQ, ActiveMQ), service meshes (Istio, Linkerd, Consul Connect), reverse proxies (Nginx, Traefik, HAProxy), caching layers (Redis, Memcached), ESBs (Enterprise Service Bus), and API gateways acting as middleware. Threats include: message poisoning, man-in-the-middle within internal networks, unauthorized topic/queue access, cache poisoning, and lateral movement exploitation via misconfigured service mesh.

**The Why:**
Middleware is the connective tissue of distributed systems. It is frequently under-secured because it is "internal." Zero-trust destroys the concept of "internal is safe." Every hop must be authenticated and encrypted.

**The How:**
- mTLS everywhere within the service mesh — Istio's PeerAuthentication policy, SPIFFE/SPIRE for workload identity
- Message broker security: ACLs on Kafka topics, SASL authentication, TLS in transit, at-rest encryption of messages
- Redis security: requirepass (AUTH command), TLS, ACL lists, bind to localhost or VPC-internal only, no public exposure
- Nginx/reverse proxy hardening: disable server tokens, enable ModSecurity WAF, set strict SSL/TLS configuration (TLS 1.2+, strong cipher suites, HSTS, OCSP stapling)
- Cache poisoning prevention: validate cache keys, use Vary headers correctly, no user-controlled cache keys
- Event-driven security: sign messages (HMAC or asymmetric), validate consumer identity, implement idempotent message processing to prevent replay attacks

**Architecture Consideration:**
Zero-Trust Internal Network Architecture — every service-to-service call is authenticated (SPIFFE identity), encrypted (mTLS), authorized (OPA/Rego policies), and audited (distributed tracing with Jaeger/Zipkin + security-aware logging).

---

### LAYER 5 — DATABASE SECURITY

**The What:**
Define database threats — SQL Injection (primary), privilege escalation, data exfiltration, unencrypted data at rest, insecure backup exposure, excessive privilege on DB accounts, MongoDB/NoSQL misconfigurations (no auth exposed to internet — the 2017 MongoDB ransomware wave), Redis without authentication exposed publicly, timing attacks on authentication queries, and side-channel attacks.

**The Why:**
The database is the crown jewel. Every other security control exists to protect what ultimately lives here — PII, financial data, credentials, intellectual property. A single misconfiguration can expose millions of records (Equifax, Capital One, Yahoo).

**The How:**
- Encryption at rest — AES-256 (Transparent Data Encryption in SQL Server, PostgreSQL pgcrypto, MySQL Enterprise TDE)
- Encryption in transit — TLS for all DB connections (no unencrypted connections allowed, enforce ssl-mode=require)
- Column-level encryption for PII (SSN, credit card, health data) — application-level encryption with key management separate from data
- Key management — HSM (Hardware Security Module) for master keys, envelope encryption pattern
- Principle of least privilege for DB users — one service = one DB user with only the permissions it needs (SELECT only? Then no INSERT/UPDATE)
- Database activity monitoring (DAM) — IBM Guardium, Imperva, pgAudit for PostgreSQL
- Row-Level Security (RLS) in PostgreSQL — enforce tenant isolation at the DB layer
- Prepared statements enforced at the ORM and driver level
- Regular backups — encrypted, tested, off-site, air-gapped for critical systems
- Database firewall — only application servers in the same VPC/subnet can connect; no direct public access
- Audit logging — every privileged action, schema change, and administrative command logged
- Secrets rotation — automated credential rotation via Vault dynamic secrets

**Architecture Consideration:**
Design a Database Security Architecture using: VPC-isolated RDS/PostgreSQL → encrypted at rest (KMS) → TLS in transit → IAM database authentication (AWS RDS IAM auth) → Vault dynamic credentials → pgAudit logging → CloudWatch/SIEM alerts → automated backup with cross-region replication. Separate read replicas from write primary; separate analytics from transactional DB.
